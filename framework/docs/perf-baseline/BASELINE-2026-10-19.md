## Experiment protocol (binding)
1. Change ONE thing per experiment; everything else byte-identical (rebuild both servers even if only one changed — same toolchain, same machine state).
2. Release-vs-Release, identical routes/workload, alternating runs (rawload order A,K,A,K...).
3. Record per-run: rps, p50, p95, p99, CPU-seconds, RAM, failures. Reuse `bench_accurate.py`.
4. Verify response bytes equality (headers required by HTTP + framing) before accepting numbers; behavior-changing speedups are invalid comparisons unless disclosed.
5. Run related tests after each change: date-format, timeouts, cancellation, keep-alive, connection close.
6. If delta ≤ noise → declare inconclusive. If no improvement → keep the honest result; do not hide.

## Experiment results log

### E1 — Date caching (response.rs, 2026-10-19)
- Change: `write_http_date_now` caches one formatted IMF-fixdate per UNIX second; replaces per-response `http_date_now()` format + allocation. Output bytes structurally identical (same field, same width, same second-granularity value).
- Tests: aether-http 76 green (incl. 2 new cache tests + fixtures); aether-tests 78 green (timeouts/keep-alive/close).
- Function-level microbench (`cargo test --release -p aether-http -- --ignored --nocapture bench_date`): uncached 0.49µs/op → cached 0.058µs/op (×8.2–8.7, 3 rounds). Saves ~0.43µs per response.
- Server-level: NOT DECISIVE. Session-2 matrix (bench-after-datecache-...noisystate.txt) shows BOTH servers ~35–40% slower than baseline session (Actix 45.6k→26.9k), i.e. machine state shifted; cross-session comparison invalid. p50 gap Aether↔Actix unchanged (~0.3ms).
- Verdict: keep (proven at function level, zero behavior change); do not claim server-level improvement.

### E1b — spawn cost measurement (no code change, `spawn_cost` bin)
- Same boxed-future shape as `AsyncHandlerFn`: direct await 0.051µs/op; spawn+await 2.77µs/op; spawn+timeout+await 2.39µs/op (2 rounds; timeout wrapper itself ≈ noise).
- Confirmed: per-handler spawn costs ~2.4–2.8µs CPU + one scheduling hop (sync handlers included — verified app.rs:597-599,1316-1327). Real, but ~50× smaller than the confirmed 150µs p50 gap → spawn alone cannot explain Actix's p50 edge. No removal without a behavior-preserving design + proof.

### E2 investigation (no code change) — corrected measurements + semantics audit
Rotated-order `spawn_cost` (3 rounds, order-permutation): direct **0.044–0.048µs**, spawn+await **1.5–2.0µs**, spawn+timeout **1.6–2.0µs**. Earlier per-order numbers (2.4–2.8) included ordering bias; the timeout wrapper itself adds ≈0.1–0.3µs. Budget: baseline server ≈ 78µs CPU/request → spawn ≈ 2–3% of request cost — modest, must not oversell.

Current-handler-execution-semantics (app.rs:1316-1336, 1539-1555) — verified facts:
1. 504 is RESPONSE-side only for blocking sync handlers: `abort()` cannot interrupt a poll-in-progress; a never-yielding future runs to completion on its worker regardless, and JoinError-vs-timeout decides the reply. Inline execution would delay even the 504 reply until the handler returns → observable behavior delta in the pathological (>request_timeout blocking sync) case.
2. Client disconnect mid-handler does NOT cancel today: the connection task is blocked awaiting `timeout(request_timeout, join_handle)`; it learns of the disconnect only at write time. Spawn provides no early-cancel here either.
3. Drain-time orphan IS real: `connections.shutdown()` (app.rs:1554) aborts connection tasks; their in-flight JoinHandles are dropped and **do not cancel** the spawned handler tasks, which keep running to completion in the background (guard accounting still happens inside the task, so stats are consistent). Confirms the reviewer's point exactly.
4. Panic isolation is real: handler panics surface as JoinError → 500 (app.rs:1329) without killing the connection task. Any inline design needs `catch_unwind(AssertUnwindSafe)` to preserve this.
5. Everything goes through spawn, sync included (route_sync wraps the closure into a boxed never-yielding future, app.rs:597-599).

Proposed E2 (awaiting approval, not implemented): inline ONLY when handler registered via `route_sync` AND no user middleware wraps it (future provably never yields); keep spawn+timeout for async handlers unchanged. Must-preserve proofs: panic→500 via catch_unwind; documented delta for blocking>timeout; wire tests written against CURRENT behavior first, then run unchanged against the new build; two-binary same-session A/B (old exe vs new exe alternating) plus the full matrix before keeping or reverting.



### Stage 0 — behavior-pinning contract tests (delivered 2026-10-19, zero production-code change)
New file `framework/tests/tests/handler_exec_semantics.rs` — 6 wire tests over real TCP, the contract Stage B must keep passing unchanged:
1. sync handler panic → 500, same keep-alive connection serves the next request.
2. async handler panic (after an await) → 500, connection survives.
3. async handler > request_timeout → 504 + `Connection: close` + socket closed AND post-sleep side effect NEVER runs (abort genuinely cancels at the await point).
4. blocking sync handler > request_timeout — **refined truth, replaces fact #1 above**: outcome is RACE-DEPENDENT, so the contract pins invariants instead of a coin flip: terminal response within 3s; either 504+close or late-200 with a still-sound keep-alive connection; blocking handler ALWAYS runs to completion (never preempted). Evidence: pure-tokio probe (`aether-bench-compare/src/bin/timeout_probe.rs`, mirrors app.rs:1316-1336) got 5/5 TIMEOUT/504 while the full Aether server got late-200 5/5 in-suite — because in the server the handler is spawned into the connection task's own worker slot; while that worker blocks inside the handler poll it cannot process ITS OWN timer shard, so the 504 can only arm after the handler returned. Standalone probe's blocked-task owner thread stayed responsive → 504. Both outcomes documented; neither may desync.
5. client disconnect mid-handler: handler completes anyway (counter hits 1), failed write tears down only that connection; server keeps serving new connections.
6. drain: keep_alive_timeout=200ms, handler sleeps 700ms → `serve_with_shutdown` returns <500ms, client socket closes with NO response, handler counter still 0 at serve-return then 1 at +600ms → orphan behavior confirmed on the wire.

Stability: contract #4 run 6× fresh (6/6 pass). Full package: aether-tests 72 green (6 semantics + 20 http_e2e + 9 scheduling + 12 test_client + 17 extractors + 8 middleware), `--test-threads=4`. No production file touched; hashes unchanged.

Stage B implications (updated): inline execution of a blocking sync handler would additionally delay the 504 AND stall the connection task's socket; today's worst case is best-effort-timeout-or-late-200. The contract accepts both, but Stage B A/B must watch tail latency under blocking handlers (fairness risk), not just average µs.

### p50 root-cause investigation (session 5, 2026-10-19) — Hamza's option (ب), no production code touched

**1. Healthy-machine CPU/request** (`bench-accurate-2026-10-19-session5-healthy.txt`, 4 alternating runs):
p50 gap reproduced: Aether 0.960/0.925ms vs Actix 0.648/0.633ms (~+0.30ms, same direction every run); RPS equal (27.2k/28.4k vs 27.9k/28.7k, inside σ). Per-request CPU (cores÷rps per run): Aether 109–116µs vs Actix 104–114µs → ΔCPU ≈ 2–11µs/req (run1/run3 Actix numbers contaminated by its own anomalous runs; median Δ ≈ 5–8µs). Amplification at observed load would multiply ΔCPU by ~2–8× at best — not the full 300µs, and directionally real.

**2. TCP_NODELAY lead — RULED OUT as differential:** grep: framework never calls set_nodelay on accepted sockets (only test clients set it on their side; rawload client sets it too, rawload.py:111/149). BUT actix-http 3.19.0 (version in bench Cargo.lock): ServiceConfig default `tcp_nodelay: None` (config.rs:207/233), actix-web 4.17 HttpServer default None (server.rs:126), only applied when Some (server.rs:665ff), and `desired_nodelay` is a plain passthrough (service.rs:28-30). actix_server.rs never calls .tcp_nodelay(). ⇒ BOTH servers leave Nagle at Windows default ⇒ symmetric; cannot explain the Aether-vs-Actix gap. (Side note: as a framework Aether may still WANT explicit set_nodelay(true) for real-world clients — separate gate decision, not a benchmark differential.)

**3. Load-shaped socket A/B** (`socket_paths-2026-10-19.rs`, run in-process: identical read/parse/write loop, ONLY difference = spawn+timeout vs inline, 12 keep-alive conns, order-rotated, 8 rounds×4k): Δp50 = **+7.6µs ± ~30µs per-round noise, signs flip round-to-round** → the hop-under-load hypothesis is bounded at ≈≤20µs (2σ). The ~100–300µs gap is NOT the spawn hop. (Absolute p50 ~480µs is harness artifact: client+server share the process/cores; only the within-harness Δ is valid.)

**4. Context-build cost, allocation-counted** (new bench `ctx_cost.rs`, mirrors app.rs:1040–1057 over a realistic 8-header request, rotated 7 rounds):
- current (two HashMaps: verbatim + lowercase-multi, owned Strings): **~2.6–3.1µs/req, 43 allocations, 2762 bytes**
- alt1 (single multi-map only): ~1.7–2.4µs, 26 allocs, 1770 bytes
- alt2 (borrowed slices, zero per-header allocation): ~0.05–0.06µs, 1 alloc (Vec spill), 256 bytes
So header materialisation is the single biggest identified CPU block in the hot path (~2.9µs/req, ~43 allocs — more than the earlier 13–16 estimate; `to_ascii_lowercase` + double map insertion dominate). Removing it saves CPU the framework genuinely spends, worth ~2–8µs/req at RPS level, but it changes RequestContext's public shape (API/behavior risk — must go through the gate as ONE change, and it is NOT the p50-gap explanation).

**Net verdict of the investigation so far:** spawn-hop NO, allocations NO (small real gain available), NODELAY NO (symmetric), scheduler NO (not in bench path), ctx copies ~2.9µs NO as full cause. The load-dependent ~100µs (sweep shape) / ~300µs (bench_accurate shape) remains UNATTRIBUTED. Next evidence-gathering candidates (no code change): per-request segment/pattern comparison of the two servers on the wire (PktMon/loopback capture), write-flush cadence, and accept-loop wake pattern. Stage B stays DEFERRED: measured expected gain from removing the hop ≈ 0–20µs p50, below the gap and near/below noise — proceeding would add behavior risk without a proven benefit.
